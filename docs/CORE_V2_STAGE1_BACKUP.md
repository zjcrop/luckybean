# Core v2 第一阶段：安全备份与隔离恢复演练

状态：第一阶段功能及本地自动验证完成；首轮 PR 必需检查通过，收尾提交仍须同 SHA 远端检查。保持 PR #142 草稿，main 暂不上线，未生成 APK。真实设备结果仍待实测。

基线：`168ab492d919f5a37e9dd9cfe2fe745db1216ee9`（Web main.19）。
本阶段独立于 #135；不修改该 PR，不切换 Room/GeckoView，不修改 schema 10，不执行实际数据覆盖恢复。

## 用户流程

入口：器设 → 数藏 → 安全备份与恢复演练。

1. 暂停编辑和同步，关闭其他富贵盒子页面。可断网操作；已加载的页面及模块应先准备完成。
2. 输入至少 12 字符的备份口令，并重复输入。该口令用于本机文件加密，不是登录密码；单独保管，无法找回。
3. 创建备份：连续读取两次业务库、照片库和白名单偏好，若观察到差异即停止；任何读表失败均不得作为空表导出。
4. 加密后立即解密，并写入唯一命名的隔离数据库；逐表读回、核对数量/SHA-256、验证私密品鉴和身份记录可解密，清理本次临时库。
5. 保存 `.lbsecure` 文件。调用下载/系统选择器只表示请求保存，不表示文件已落盘。
6. 重新输入口令，选回实际保存的文件，再执行解密与隔离恢复演练。只有此步成功才具有文件读回证据。
7. 导出诊断记录；备份保存在本机及独立副本，不能提交到 GitHub。

## 覆盖范围和边界

- 业务库全部 13 个 schema 10 表的原始记录和键，包括回收站、outbox、历史版本、派生摘要和 syncMetadata 中的恢复密钥。绕过会在解密失败时返回占位内容的业务读取层。
- `luckybean-local-assets/beanThumbnails` 全部照片，保留原始字节及豆卡键，包括尚未清理的孤立照片。
- localStorage 白名单：当前及兼容版外观、语音、分组方式、选中豆卡、浮动按钮位置。
- 不保存登录会话、未保存的识别图片、临时批次、网络缓存及未列明的 localStorage 状态。备份并不声称复制整个浏览器配置。
- AES-256-GCM；PBKDF2-SHA256（310,000 次），随机 16 字节盐、12 字节 IV；认证头禁止 KDF 参数降级。口令不持久化，UI 操作结束清空口令框。
- 类型编码后的快照上限 64MB；加密文件因 Base64 会增大。可选字段 `undefined`、缺省字段、`null`、稀疏数组及负零分别无损保存、参与哈希；首轮普通 JSON 负载的加密文件仍可读取。未知 schema、未知章节、重复键、损坏数据或未支持的类型（如 Date、二进制对象、非有限数和循环引用）均停止，不静默丢字段。
- 两个数据库无法共享一个 IDB 事务；双次比对仅能发现观察到的变化，不能替代暂停写入，也不宣称跨数据库全局事务快照。
- 隔离演练验证原始行的写入/读回和密文可读性，不会启动一份独立完整应用，不代表生产恢复、索引重建、迁移回滚或实体设备升级已验收。新格式没有实际覆盖恢复入口；该入口须在后续有恢复日志和实机证据的阶段交付。
- 临时数据库在成功和异常退出路径均尝试删除；若进程被系统直接终止，finally 无法运行，可能遗留本次演练库。不会自动清理其他数据库；此时仍不能将演练标为通过。
- 原有 `.luckybean` 便携数据备份/恢复继续兼容。仅修正导出吞掉读表异常以及解密占位记录的问题；旧格式仍不含独立照片，新入口对此作了说明。

## 诊断及失败证据

诊断包含阶段、失败步骤、时间、应用元数据版本、数量、哈希、私密记录验证数量；不包含记录正文、照片字节、口令、密钥、文件名或异常原文。
成功报告明确 `liveRestore=not-performed`、`deviceAcceptance=pending`，不会自动勾选 #135 实机验收表。
诊断追加保存，不用新成功覆盖旧失败。若 localStorage 已满，当前会话仍保留可导出的内存记录；请立即导出，退出页面后内存记录会丢失。

## 分阶段上线安排（2026-10-14）

用户要求本轮继续完成第一阶段、不生成 APK、main 可以暂缓，上线后再检验各设备。因此本轮完成候选与自动门禁，不合并、不部署；建议下一次仅将本阶段作为独立 Web 版本上线 main，不等 Room/GeckoView 一起交付。

| 阶段 | 范围 | main 上线时点与下一步门禁 |
|---|---|---|
| 1 | 安全备份、文件读回、隔离行级恢复演练 | 功能及必需检查通过后，可单独发 Web；上线后完成下表各设备验收，问题先在本阶段修复 |
| 2 | 新存储旁路验证与可审计的迁移/恢复日志 | 第一阶段设备验证通过后再拆分实施；保持旧存储为主。涉及 Room 的设备验证须以后明确允许 APK，再独立安排 |
| 3 | 正式存储切换 | 具备真实 schema 10 数据设备上的覆盖升级、迁移、回滚证据后再单独发布，不凭自动测试切换 |
| 4 | GeckoView 引擎切换 | 存储阶段稳定后再独立交付、实测，避免同时变更存储与引擎 |

发布第一阶段前：重读 main/PR head → 建立并校验源码备份 → 确定独立 Web 发布版本 → 对最终待合并源码运行必需检查 → 合并后核对同 SHA 主测试、Pages 部署回执及线上检查。任何 SHA 变化均重新确认适用检查；不将 PR 合成提交结果冒充 main 发布结果。保持 Android 构建关闭，保留失败记录。若部署或线上验收失败，停止后续阶段，不清理浏览器数据。

第一阶段上线后的多设备浏览器验证不等于 Android 安装包升级验证：网页与旧 APK 的本地数据位置不同，不能从网页读出 APK 私有数据库。旧 APK 不卸载、不清数据；#135 仍为草稿，#22 保持开放，其完整实机表不能被本阶段结果自动勾选。
