# LuckyBean 1.23D 开发与验收手册

版本：1.23D / Handbook v1.1  
制定日期：2026-08-08  
适用主线：`main`  
行为基线：LuckyBean 1.2.3-brewprofiles-integration-test  
当前工程检查点：LuckyBean 1.23D-recognition-contract.2

> 本手册是 LuckyBean 1.23D 后续开发、测试和交付的执行基准。`DEVELOPMENT_STATUS.md` 记录当前检查点，本手册管理完整需求、优先级、依赖关系、验收口径和发布门禁。两者冲突时，以本手册中较严格的验收标准为准。

## 1. 目标与基本原则

LuckyBean 当前不推进到 2.0，先在 1.2.3 Web/PWA 行为基线上完成 1.23D 的问题修复、回归验收和可交付测试版本：

- 当前主产品：Web/PWA 与既有 Android WebView 测试壳，继续使用 IndexedDB 和现有业务代码。
- 当前任务：严格按问题清单逐项修复，先完成识别、分享、推荐、品鉴、复刻、语音、云同步与 BrewProfiles 闭环。
- 未来原生化：Kotlin、Compose、Room、CameraX、SAF 与 KMP 方案保留为以后独立立项，不是 1.23D 的进入或退出条件。
- 契约可迁移：字段定义、业务规则、编码表、归档格式、测试样本和预期结果仍保持平台无关，避免未来复制错误规则。
- BrewProfiles：私有服务端返回权威计算；LuckyBean 本地负责缓存、离线降级、执行过程和 3D 渲染。计算访问不依赖云同步账户 JWT。
- 账户：不建立第二套应用账户，只保留服务器同步登录；游客可完整管理本地数据。
- 数据安全优先：任何迁移、同步、恢复都不得造成豆卡、克重、历史记录、关联 ID 或隐私数据静默丢失。
- 识别正确性优先：低置信度字段宁可留空并请求确认，不得为了提高“自动填充率”而错填。

## 3. P0：豆袋识别与字段归属重构

### 3.1 已确认的原缺陷（1.23D 第一检查点已代码修复，待完整验收）

1. `codebook.js` 使用 `labeled.roastDate || labeled.productionDate`，会把生产日期主动填入烘焙日期。
2. 文字解析完成后使用 `merged.roastDate ||= todayISO()`，无法确认日期时会静默写入当天日期。
3. OCR 已返回 `polygon`、`imageId` 和逐块置信度，但拍袋流程只把 `fullText` 交给现有解析器。
4. 照片的 `front/back/side/date` 角色没有进入字段归属计算。
5. 当前块去重以规范化文字为主键，相同文字跨照片出现时可能被合并，丢失照片来源和空间证据。
6. 日期正则主要识别 `20xx` 年开头的单一格式，不能完整覆盖豆袋常见日期写法，也没有解决 `DD/MM` 与 `MM/DD` 歧义。
7. 当前流程偏向“找到一个值就填写”，没有先保存全部候选、冲突和排除理由。

### 3.2 强制修复规则

- 删除生产日期到烘焙日期的回填规则。
- 删除识别流程中的“未识别到日期则默认今天”。手工新建表单是否默认今天可单独设计，但不得污染 OCR 结果。
- `productionDate`、`packDate`、`bestBefore`、`expiryDate` 和 `harvest` 是独立类型，对 `roastDate` 构成强排除证据。
- `Best Before/EXP/MFG/PKD/Crop` 邻近的日期不得自动进入烘焙日期。
- 无标签孤立日期只能作为待确认候选，不得静默覆盖已有字段。
- 未来日期允许输入；有效日历校验通过后显示“未来烘焙日期”警告，不得一律判错。
- 不能从到期日、保质期或建议赏味期反推烘焙日并自动保存。任何推断只能作为解释性建议。

### 3.3 结构化识别数据契约

Web 与 Android 的 OCR 输出必须统一映射为：

```text
RecognitionDocument
  documentId
  images[]
    imageId
    role: front | back | side | date
    width / height / quality
  blocks[]
    blockId
    imageId
    imageRole
    text
    confidence
    polygon[]
    normalizedBox { x, y, width, height }
    lineIndex
  fullText                 仅用于显示，不作为主解析输入
```

去重必须保留 provenance：同一文字在不同照片、不同位置或不同置信度下均保留；只能合并同一图片内高度重叠且内容等价的重复检测框。

字段解析输出必须是候选集合，而不是直接表单值：

```text
FieldCandidate
  candidateId
  fieldType
  normalizedValue
  rawValue
  sourceBlockIds[]
  sourceImageIds[]
  detectedLabel
  labelRelation: same-line-right | below | same-region | none
  formatConfidence
  ocrConfidence
  semanticConfidence
  spatialConfidence
  conflictFlags[]
  exclusionReason
  finalScore
  decision: auto-fill | confirm | reject
```

### 3.4 日期候选处理流程

1. **候选提取**：从每个 OCR block 及相邻 block 组合中提取所有日期，不立即填表。
2. **字符纠错**：只在日期上下文中尝试 `O→0`、`I/l→1`、`S→5`、`B→8`；纠错后必须是有效日历日期。
3. **格式标准化**：支持 `YYYY-MM-DD`、`YYYY/MM/DD`、`YYYY.MM.DD`、`YYYYMMDD`、两位年份、中文年月日、英文月份在前/在后。
4. **歧义保留**：如 `03/04/26` 无法由标签、地区或品牌模板唯一判断，保留两个候选并要求确认。
5. **标签分类**：使用严格标签词典区分 roast、production、pack、best-before、expiry、harvest。
6. **空间绑定**：同一行右侧最高，标签正下方次之，同一区域再次；全文远距离匹配不能自动填入。
7. **照片角色加权**：`date` 照片提高日期候选权重，但不能覆盖明确的非烘焙日期标签。
8. **冲突检查**：同图或跨图存在多个不同烘焙日时，禁止自动填充。
9. **决策**：只有“明确烘焙标签 + 空间相邻 + 有效日期 + 无冲突”才允许自动填充。
10. **用户确认**：中等置信度候选显示原文、照片角色、局部位置和分类选项；用户可选“烘焙日期/包装日期/最佳赏味期/忽略”。

初始门槛建议如下，最终阈值必须通过真实样本校准：

| 最终分数 | 行为 |
| --- | --- |
| `≥ 0.88` 且无硬冲突 | 自动填充，表单标明证据 |
| `0.65–0.879` 或存在可解释歧义 | 请求确认 |
| `< 0.65` 或命中硬排除 | 不填或拒绝 |

### 3.5 其他数值字段同步治理

同一候选框架必须用于海拔、净重、价格、Agtron 色值、批次号和产季，防止数字串位：

- 海拔必须邻近 `Altitude/Elevation/海拔/masl`，单位换算可追踪。
- 净重必须邻近 `Net Weight/净含量`，不能把袋装规格误当剩余克重。
- 价格必须有币种或价格标签；孤立数字不得自动填价格。
- Agtron 必须在合理范围且邻近色值标签；不得把海拔或批次数字当色值。
- 批次号按字符串保存，不进行数值化和日期化。
- 产季支持单年和跨年表达，但永不作为烘焙日期。

### 3.6 识别验收数据集

建立版本化、去隐私的黄金样本集（2026-08-08 用户决定不再作为 1.23D 本次部署阻断门禁，保留为后续抽样质量改进）：

- 不少于 100 组豆袋，覆盖中文、英文及中英混排。
- 每组包含原始图片角色、OCR blocks、人工标注字段和预期决策。
- 至少 30 组含两个或更多日期；至少 15 组含 MFG/PKD/EXP/Best Before；至少 10 组含跨年产季。
- 包含反光、曲面、倾斜、低对比、点阵喷码、两位年份和模糊字符。
- 本次附带的人物照片不得作为识别样本。

P0 验收门槛：

| 指标 | 门槛 |
| --- | --- |
| 明确标注的烘焙日期准确率 | ≥ 98% |
| 非烘焙日期误填为烘焙日期 | 0 次 |
| 多日期场景的静默错填 | 0 次 |

## 4. 未关闭业务问题的验收清单

### 4.1 分享

- 豆卡详情分享按钮每次可响应，不受页面重渲染影响。
- 二维码、链接、HTML 文件三种方式分别测试。
- 分享内容包含约定的最近 5 条冲煮与最近 5 条品鉴；不足 5 条时不得填充虚假记录。
- 编码后再解码，豆卡核心字段和关联记录等值。
- 超长链接明确降级为 HTML 文件，按钮和提示一致。
- Android 使用系统分享与 SAF；Web 使用下载/剪贴板能力，权限失败有可恢复提示。

### 4.2 推荐与豆卡列表

- `renderBeans()` 保持单一职责和唯一入口，禁止再次通过后加载脚本覆写同名函数。
- 推荐状态的数据字段、DOM 属性和 CSS 类建立单一映射，不允许 `is-recommended` 一类命名漂移。
- 测试“荐”FAB、豆卡标记、排序、分组、筛选、展开/收起、刷新和空列表。
- 推荐结果必须能解释依据；随机推荐应明确标记随机，不伪装成模型推荐。

### 4.3 品鉴、修正与复刻

- 品鉴完成后，返回、刷新、重启均保持完成状态。
- 自动分与主观分分开保存，不相互覆盖；算法版本随记录保存。
- 低分修正方案必须引用来源品鉴记录和来源冲煮记录。
- 修正草案在用户确认前不得改写历史冲煮。
- 复刻恢复完整阶段数组、总水量、粉量、温度、研磨设备/刻度、研磨圈数、滤杯、滤纸和自定义微调。
- 复刻后形成新 session ID，不覆盖原记录；来源关系可追溯。

### 4.4 语音

- 播报必须支持暂停、停止、应用退后台和来电/音频焦点中断。
- 语音输入权限拒绝后可继续手工录入。
- 不得把浏览器存在 `speechSynthesis` 当作 Android 真机通过。
- 设备无离线语音包时明确说明，不得静默请求外部服务。

### 4.5 BrewProfiles、3D 与降级

- 同一输入的请求参数、服务端模型版本、返回结果和本地缓存键可追溯。
- 服务端超时、无网、401/403、5xx 和不兼容版本分别处理。
- 缓存命中时显示计算时间与模型版本；过期缓存不得伪装为实时权威结果。
- 本地参考分析必须明确标注“离线参考”，不能与权威计算混淆。
- 3D 渲染失败不应破坏方案本体和历史记录。

### 4.6 云同步

- 本地记录先写入本地数据库，再进入同步队列。
- 同一操作重复上传必须幂等。
- 覆盖远端记录前按稳定 ID 与版本校验，不以名称或日期猜测同一记录。
- 删除采用可恢复 tombstone/回收站策略；离线删除与远端修改冲突可见。
- 同步登录会话与设备密钥不进入 `.luckybean` 归档。

## 5. 数据契约与迁移

### 5.1 先固化的核心实体

1. `Bean`：豆卡静态属性、烘焙日期、初始/剩余克重、冷藏状态、来源与识别证据。
2. `BrewSession`：完整变量、阶段、执行状态、计算版本、来源方案和复刻关系。
3. `SensoryRecord`：主观分、自动分、札记、缺陷、偏好输入和来源 session。
4. `InventoryEvent`：购入、冲煮消耗、修正、归零、恢复与手工调整。
5. `RecognitionDocument`：图片角色、OCR blocks、候选、用户确认和解析器版本。

### 5.2 Schema 要求

- 每个字段定义类型、单位、可空性、默认值、枚举、范围和迁移行为。
- 重量使用明确精度，不以浮点累计值直接作为库存真值；库存由事件与校验快照共同保证。
- 时间统一保存 ISO 8601；“日历日期”和“时间戳”分型，烘焙日期不得受时区转换影响。
- 所有实体使用稳定 UUID；显示名称、日期和用户 ID 不参与主键生成。
- 每条计算和解析结果保存算法/词典/模型版本。
- Android Room 与 Web IndexedDB 对同一归档字段的缺省语义必须一致。

### 5.3 黄金迁移测试

构造 1.2.3 固定数据库样本，至少包含：

- 正常豆卡、字段缺失豆卡、未来烘焙日期豆卡、归零豆卡和冷藏豆卡。
- 多次冲煮、复刻、修正、品鉴、库存事件和分享草稿。
- 自定义编码、历史修订、回收站与待同步队列。
- 隐私字段与重新加密场景。

迁移前后逐项比较：记录数量、稳定 ID、外键关系、克重、日期、阶段数组、历史链、算法版本和哈希。任何静默丢失均阻断下一阶段。

## 6. 分阶段实施流程与门禁

每一阶段必须完成“实现 → 自动测试 → 人工验收 → 交付物 → 状态更新”，不允许只有代码或口头说明就进入下一阶段。

### 阶段 A：1.2.3 行为基线与问题冻结

实施：

1. 将本手册中所有未关闭问题登记为唯一 issue ID。
2. 建立关键业务最小回归测试：分享、推荐、品鉴、修正、复刻、归档。
3. 保存 1.2.3 黄金数据和截图/操作预期。

退出门禁：问题清单无重复、无“已实现=已通过”的状态；黄金样本可重复运行。

交付物：问题矩阵、自动测试报告、Web 本地预览。

### 阶段 B：结构化识别与日期归属 P0

实施顺序：

1. 删除生产日期回填和 OCR 默认今天。
2. 建立 `RecognitionDocument`/`FieldCandidate` 契约。
3. 保留 blocks、坐标、照片角色和 provenance。
4. 实现日期候选提取、分类、空间绑定、冲突和确认 UI。

## 7. 测试矩阵

| 层级 | 必测内容 | 运行时机 |
| --- | --- | --- |
| 单元测试 | 日期解析、字段分类、评分、归档、迁移、库存计算、编码 | 每次提交 |
| 契约测试 | JS/Kotlin DTO、Schema、错误码、BrewProfiles 请求响应 | 每次契约变化 |
| 数据库测试 | Room/IndexedDB 事务、升级、回滚、并发和幂等 | 每次数据层变化 |
| 组件测试 | Compose/Web 表单、候选确认、权限与错误态 | 每次 UI 变化 |
| 端到端测试 | 新建豆卡→冲煮→品鉴→修正→复刻→分享→备份恢复 | 每个检查点 |

测试报告必须记录：版本、提交、设备/浏览器、输入数据、预期、实际、证据和未通过项。只写“测试通过”不构成有效报告。

## 8. 完成状态与 Definition of Done

统一使用以下状态，禁止混用：

| 状态 | 含义 |
| --- | --- |
| 未开始 | 没有进入实现 |
| 实现中 | 尚不可验收 |
| 代码完成 | 代码存在且通过静态检查，未证明业务正确 |
| 自动测试通过 | 规定的自动测试通过，未完成真机/人工闭环 |
| 真机验收通过 | 指定设备上完成完整流程 |
| 已关闭 | 自动测试、人工/真机验收、文档和交付物全部完成 |

一个问题只有同时满足以下条件才能标记“已关闭”：

1. 有唯一 issue ID 和明确验收条件。
2. 实现不依赖未提交的本机文件、模型或密钥。
3. 自动测试覆盖正常、边界、冲突和失败路径。
4. 涉及相机、文件、语音、同步时完成真机或真实服务验收。
5. 没有破坏 1.2.3 黄金行为和已有数据。
6. 状态文件、变更说明和已知问题同步更新。
7. 对应 APK/Web 测试入口可访问，并提供版本号和 SHA-256。

## 9. 开发纪律

- `main` 是唯一开发与测试主线；达到发布标准后直接标记 Release。
- 每次改动只关闭一组有共同依赖的问题，避免大范围无回归重写。
- 先写失败测试，再修复已确认缺陷；修复后保留回归样本。
- 业务规则不得散落在 UI 事件中；放入可测试的 domain/shared 层。
- OCR 原始证据、解析候选和最终用户选择分层保存，不用最终值覆盖证据。
- 日志不得包含完整豆袋图片、登录令牌、设备密钥或不必要的个人信息。
- 私有服务密钥不得进入客户端；客户端只能使用受限、可轮换的访问机制。
- 任何“降级”必须在 UI 中可见，不能把参考计算、缓存或手工值显示成权威实时结果。
- 人物照片、无关附件和未获明确用途授权的素材不得进入工程或测试数据。

## 10. 每个检查点的固定交付格式

每次交付必须同时给出：

1. 当前版本与基线版本。
2. 本次关闭的 issue ID；未关闭问题继续列出。
3. 代码变更摘要，区分新增、修复和迁移。
4. 自动测试数量、失败数量和完整测试报告。
5. 真机设备、系统版本与实际通过流程。
6. 数据迁移和回滚结果。
7. APK、Web 测试页或源码包的准确用途，不得相互冒充。
8. 文件 SHA-256、构建提交和构建时间。
9. 已知限制、依赖缺口和下一检查点进入条件。
